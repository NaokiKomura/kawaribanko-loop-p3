# cycle 7 開発日誌

## 今回やったこと

- 平たい「版 N」を、親子の深さと兄弟枝をインデントで追う改訂帳へ替えた。各子には親版からの見出し・本文・日付・気分・返信先の旧値／新値を出し、選択中版とその返信元・返事も既存カードで同じ表示文脈に残した。
- `causalView()`を改訂グラフだけから作る純粋関数として追加し、複数階層・兄弟枝・保存配列を逆順にしたケースでも表示モデルが変わらないNode回帰を書いた。
- 書き直し中の親をフォーム上に明示し、新規投稿へ戻る解除を追加した。版間差分をプレビューに旧値／新値で出し、同じ差分関数を使って無変更の子改訂をプレビューと保存の両方で拒否した。

## なぜその判断をしたか

レビューが求めたのはボタンの見た目を変えることではなく、取込順に左右されず因果を読めることだった。保存配列を並べ替える案は取込由来の偶然をUIへ持ち込むため採らず、親IDで木を組んで決定的な改訂IDで兄弟を並べた。未変更判定もフォーム側だけに置くと保存経路からすり抜けるので、保存関数とプレビューが同じ`describeRevisionPair()`へ寄る形にした。正本はこの変更でも一切編集可能にしていない。

## 詰まった点と、どう解決したか

改訂中に日付を毎回「今日」へ作り直す従来の下書きでは、内容を触らなくても日付差分だけで空の枝を作れてしまう。書き直しでは親版の日付を保つようにし、表示上の無変更と保存上の無変更を一致させた。HTTP確認は`python3 -m http.server`を127.0.0.1の別ポートで起動してもソケット作成が`Operation not permitted`となり、この環境ではできなかった。代わりにNode回帰、構文、JSON、参照ファイル、差分空白を確認した。繰り返し作業を切り出す必要はないと判断し、スキルや補助スクリプトは追加していない。

## 次サイクルの自分への申し送り

因果ビューを保存配列順へ戻さない。次は世代番号によるread-before-writeを全保存経路へ入れ、古いタブが上書きしない回復手段を画面に出す。その上で取込だけのundoを、前提世代付きappend-only操作ログの複数段undo/redoへ置き換える。来歴と「ハッシュは署名でない」限界も書出しと取込の判断に接続し、v1/v2/v3移行、書込例外、競合をNodeで残すこと。
