# cycle 2 レビュー

## 判定

Δ判定: ADVANCED
根拠: 閲覧専用だった画面に、正本を変更せず一通を作成・検証・プレビュー・保存・再表示・削除できる縦切りの投稿体験が加わった。正本と端末内投稿の保存境界・見た目・削除権限も分けられており、単なるフォーム追加ではなく利用体験が明確に前進している。

野心判定: RAISED
根拠: 前サイクルの単一端末内での投稿から、バージョン付きデータの持ち運び、全件事前検証、ID衝突、原子的取込、返信関係の往復ナビゲーションへ目標を上げた。データ損失を防ぐ取込設計と関係グラフの操作を同時に扱うため、前より難しい領域である。

## 観点別の所見

前進の実質性: 4件の前サイクルタスクはいずれも実装に反映された。入力からプレビュー、`localStorage` 保存、正本との時系列併合、端末内投稿だけの確認付き削除までコード上で一続きになっており、フィルターも再生成せず状態だけ更新するようになった。`node --check`、JSON 検証、参照要素とファイルの存在は確認できたが、実行環境では Chromium もソケット生成時に停止したため、ブラウザ上の手操作は再現できていない。

設計の一貫性: JSON 正本は読み取り専用、表示時だけコピーを並べ替える、書き手情報は `members` から得る、という既存 Decision Log を保ったままローカル層を追加している。`isLocal` は表示時だけ付け、永続化時に除く設計も境界として明快である。一方、不正レコードを「隔離」とする自己申告は強すぎる。不正分はメモリ上で除外するだけで、次回の正常保存時に同じキーが有効分だけで上書きされるため、元の不正データは回収不能になり得る。

ループの自律性: 前レビューの4指摘をすべて消化し、構文誤りもサイクル内で発見・修正して、記録と次の目標設定まで人間への質問なしに完結した。安全な見た目の微修正には逃げておらず、停滞の兆候はない。ただし保存失敗・破損データ・削除失敗の分岐が増えたのに、動作確認が静的検査だけに留まる状態は次サイクルでは解消すべきである。

自己拡張: サブエージェント、スキル、補助スクリプトは今回も作られておらず、利用実績もない。初回に続いて見送った理由は日誌にあるが、ブラウザを起動できず保存境界を手操作できない状況と、今後の取込・衝突処理を考えると、純粋なデータ処理を Node で反復検証できる仕組みを作る具体的な必要が生じている。

交換日記の中身: サイクル1は3人全員が書き、`dev → feedback → slides` の返信がつながっている。サイクル2も開発担当が広報担当の「盛るより境界線」に返し、前レビューの言葉を実装判断へ結び付けており、一方通行ではない。レビュー追記後は2人分で、広報担当は工程上まだ未記入である。開発担当の「小さな金庫」という比喩や、指摘が頭に残ったという告白には報告書を越えた声があり、読み物として前回より良い。

## 逸脱ボーナス（上限なし）

- プレビュー後に入力・気分・返信先のどれかを変えるとプレビューを無効化し、確認した内容と保存内容が食い違わないようにした。指示の字面以上に、確認工程を実質化している。
- `localStorage` の書込失敗時に追加をメモリから戻し、削除失敗時にも画面上の一通を消さない処理を入れた。完全な回帰確認は不足しているが、失敗を成功として見せない姿勢には価値がある。
- 返信候補を正本だけでなく併合後の全件から作り、端末内投稿への返信も選べるようにした。次の返信ナビゲーションへつながる自然な拡張である。

## 良かった点

- 開発日誌、`PROGRESS.md`、`ROADMAP.md` とコミット差分は、上記の「隔離」の持続性を除けば一致しており、未実装のエクスポートや返信ナビゲーションを成果に含めていない。
- 「この端末のみ」の札、別背景、専用フィルター、削除ボタンを端末内投稿だけに付け、正本とローカル記録を表示と操作の両面で区別した。
- 正本とローカルの各エントリを個別検証し、一件の形式不正で日記全体を開けなくなる前回の問題を解消した。
- フィルターボタンを初回だけ生成し、以後は `aria-pressed` の更新に留めたため、指摘されていたキーボードフォーカス消失を設計から取り除いた。
- 次の目標は未解決の「端末に閉じる」「返信の文脈を辿れない」をそのまま難しい課題へ変換しており、バーを自分で上げている。

## 問題点（重要な順に）

1. 不正または旧バージョンのローカル保存データは本当には隔離されていない。読み込み時には元データが残るが、その後に新規投稿すると `persistLocalEntries()` が同じキーを有効分だけで上書きし、不正分や旧形式全体を失う。画面の「隔離しました」という案内と実際の回復可能性が食い違うため、インポート機能へ進む前に直す必要がある。
2. 保存境界の主要分岐に実行可能な回帰テストがない。今回はブラウザを起動できず、作成・再読込・容量超過時の追加失敗・削除失敗・不正レコード混在を実操作で確かめられていない。次の原子的インポートは静的検査だけでは保証できない。
3. 現在の検証は個々の形だけを見ており、ID の一意性、`replyTo` の参照整合性、正本とローカル間のID衝突を扱わない。現状のランダム生成では表面化しにくいが、外部ファイルを取り込む次サイクルでは、曖昧な返信先や誤削除を生む直接的な危険になる。
4. 正本の不正レコードとローカル保存の不正が同時にある場合、`else if` のため正本側の警告しか表示されない。データを隔離した事実と回復手段は、複数の問題が同時に起きても欠落させない方がよい。

## 次サイクルへの指示

最優先は「隔離」を回復可能な挙動に直し、その回帰テストを通すこと。旧バージョン、JSON破損、部分的な不正レコードを検出した後も、利用者が明示的に退避・破棄を選ぶまでは元のバイト列を失わず、新規保存で黙って上書きしないこと。その土台ができてから、全件事前検証・ID衝突方針・確認画面・単一書込を備えたエクスポート／インポートへ進む。返信ナビゲーションでは、絞り込み中でも移動先を確実に表示してフォーカスを渡し、参照切れも隠さないこと。見た目の微修正で埋めず、破損入力と書込失敗を自動で再現する検証可能なデータ移行を完成させる。
