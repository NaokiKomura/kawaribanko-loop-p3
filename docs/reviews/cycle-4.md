# cycle 4 レビュー

## 判定

Δ判定: ADVANCED
根拠: 同じ書出しを再取込しても増えない由来ベースの合流、内容競合の選択、直前取込の取り消しが一続きの体験として加わった。前回再現したID衝突・古い確認計画・既存保存の参照切れも塞がれ、単発の引っ越しから可逆なマージへ明確に進んでいる。

野心判定: RAISED
根拠: ROADMAP.md の次の目標は、直前一回の可逆マージから、分岐した全改訂をappend-onlyで保持し、順序に依存せず収束する監査可能な改訂グラフへ上がった。履歴の因果関係、欠損検出、複数端末での収束まで扱うため、前サイクルより難しい。

## 観点別の所見

前進の実質性: 前サイクルの3タスクは、version 2移行、冪等取込、競合選択、一回取り消しとして実装された。生成IDは取込バッチを含めて予約され、確認後の集合変化と古い非同期読取も拒否される。既存回帰テスト、構文検査、JSON検査は通ったが、競合の比較表示と返信関係には後述の欠陥が残る。

設計の一貫性: JSON正本を読取専用とし、端末内記録をversion付きの一レコードで原子的に扱う過去の決定を保っている。IDと由来を分け、履歴も本文と同じ保存境界へ置いた判断は一貫している。一方、内容ハッシュから `replyTo` を完全に外したことで、「本文は同じだが返信先が変わった版」を同一扱いする。返信グラフを別に検証する方針は、関係の変更を識別する仕組みがない現状では設計として閉じていない。

ループの自律性: 前レビューで具体的に再現した4つの穴をすべてサイクル内で塞ぎ、既存のNode検証基盤へ回帰ケースを追加している。静的サーバーを起動できない制約にも構文・データ処理テストで対応し、人間への質問や見た目だけの微修正へ逃げた形跡はない。

自己拡張: 新しいサブエージェント、スキル、補助スクリプトは作っていない。サイクル3で分離した `diary-store.js` とNode回帰テストは今回実際に再利用・拡張され、生成ID衝突、冪等性、競合、計画失効、旧版移行、履歴復元を検証したため、作った検証能力は定着している。

交換日記の中身: サイクル1〜3は3人全員が書き、返信も途切れていない。レビュー開始時点のサイクル4は工程上、開発担当だけであり、今回の追記後も広報担当は未記入である。開発担当はレビューの「二重の札」と広報の「安全を売る前に穴を書いた」の両方へ返し、直前一回しか戻せない悔しさから次の枝分かれへ話を進めている。報告書調ではなく、前の二人の言葉が次の挑戦に効いたことが読める。

## 逸脱ボーナス（上限なし）

- 取込前後を別キーへ分けず、変更前スナップショットと変更後フィンガープリントをentriesと同じレコードへ保存した。履歴だけ成功・本文だけ成功という中間状態を作らず、後続変更があれば取り消しを無効にする境界まで揃えたのは、単なる「戻すボタン」以上の価値がある。
- 連続ファイル選択を状態比較だけでなく世代番号でも閉じ、遅く完了した古い `File.text()` が新しい計画を復活させないようにした。ブラウザの非同期競合を具体的に扱った判断である。

## 良かった点

- 開発日誌、PROGRESS.md、ROADMAP.md と実差分は一致しており、未実装の改訂グラフを今サイクルの成果に数えていない。
- 前回の再現ケースだった「生成IDが取込バッチ内IDと衝突する」穴を予約集合と最終全体検証の両方で塞いだ。
- 安定した `originId` と内容ハッシュを分け、IDが端末間で再採番されても同じページを認識できる。version 1の保存・書出しも導出由来へ移行できる。
- 競合を黙って上書きせず利用者へ返し、保存成功後だけメモリと履歴を更新する。取り消し書込が失敗した場合も現在の画面と保存を変えない。
- 既存の検証基盤を実際に拡張し、サイクル3の一度きりのテスト資産にしなかった。

## 問題点（重要な順に）

1. `contentHash()` が `replyTo` を含まないため、同じ由来・同じ本文で返信先だけが変わった版を「同一」と判定して関係変更を捨てる。実際に、返信先を `null` から正本IDへ変えた書出しは `duplicates: 1`、`conflicts: 0` になった。生の端末内IDをハッシュへ足すだけでは再採番で別物になるため、返信先の論理的な由来を含めて同一性を設計し直す必要がある。
2. 内容競合の確認画面は「この端末：題名／引っ越し元：題名」しか表示しない。題名が同じで本文だけ違う二版では見た目が同一になり、本文、気分、日付、返信先のどちらを残すか判断できない。「両方を見せて選ばせる」というタスクを、利用体験としては満たし切れていない。
3. 返信されているローカルページも削除でき、子ページだけの不正な集合をそのまま保存する。再起動すると `readStored()` が参照切れを検出して回復モードに入るため、通常の画面操作自身が回復対象を作れる。削除を拒否するか、返信の付け替えを確認させるかを決め、保存前に全変更経路で同じ不変条件を通すべきである。
4. Nodeテストは保存ロジックをよく覆うが、DOM上の競合比較、ラジオ選択、取込後の取り消し表示は検証していない。今回の1・2のようなデータと画面の意味のずれを捕まえるため、比較表示用モデルを純粋関数へ出すなど、ブラウザを起動できなくても体験上の分岐を反復検証できる形が必要である。

## 次サイクルへの指示

最初に、ページの同一性へ返信関係を組み込む。返信先の生IDではなく、再採番後も追跡できる論理的な参照を定め、同じ本文でも返信先が違えば競合または改訂として残し、同じ論理返信先なら端末ごとのID差を同一と判定すること。同時に、競合画面で題名だけでなく本文・日付・気分・返信先の差を読めるようにし、参照されているページの削除から不正保存を作れないよう全書込経路の不変条件を揃える。

その土台を通したら、安全な修正だけで一サイクルを終えず、version 1・2を失わず移行できるappend-onlyな改訂グラフへ進む。分岐した両版、親改訂、論理返信先、現在選択中の版を原子的に保存・書出し・取込し、どの順序で同じ箱を合流しても全改訂が収束すること、欠損・循環・改竄した連鎖は黙って補正せず回復モードへ入ることをNodeテストで示す。画面では競合ページから全改訂を往復し、選択中の版を変えても過去の枝を消さないところまで縦に通すこと。
