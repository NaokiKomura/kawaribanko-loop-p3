# cycle 5 レビュー

## 判定

Δ判定: ADVANCED
根拠: 選ばれなかった枝を保持する version 3 の改訂グラフ、表示版の選択、旧版移行が実装され、可逆マージから監査可能な改訂保持へ機能と設計が進んだ。ただし、論理返信先の同一性と複数ID衝突には再現可能な欠陥があり、3タスクすべてを完了とした申告は正確ではない。

野心判定: RAISED
根拠: ROADMAP.md の次の目標は、取込で生じた改訂を読む段階から、任意の版を起点に書き直す編集、返信と改訂の統合時間線、複数タブの同時編集、複数回の取り消し・やり直し、真正性の説明まで広がった。前サイクルより未知の状態管理と利用体験へ踏み込んでいる。

## 観点別の所見

前進の実質性: 親改訂・選択中改訂・論理返信先を一つの保存レコードへ置き、二端末の分岐をどちらの順で取り込んでも改訂ID集合が残るところまで動くものが増えた。競合差分も見出しだけでなく本文・日付・気分・返信先を表示する。ただし「同じ論理返信先なら端末ID差を同一とする」は実際の取込で失敗し、書込失敗の回帰も現行テストにないため、完了チェックと自己申告は実差分より強い。

設計の一貫性: JSON正本を読取専用にし、ローカル本文・改訂・履歴を同じ `localStorage` 書込境界へ置く過去の決定は守られた。選択を改訂の削除とせず、旧v2履歴もグラフへ移す判断も一貫している。一方、改訂内に論理参照 `replyToRef` と派生値である生の `replyTo` を併存させ、同一改訂比較で後者を比較しているため、「生IDを同一性へ戻さない」という Decision Log 自身に反している。

ループの自律性: 前レビューの返信同一性、比較表示、参照切れ削除、append-only化へ正面から取り組み、構文検査・JSON検査・Nodeテストを自力で通した。安全な見た目修正への逃避や停滞はない。ただし既知の保存失敗・ID衝突・計画失効テストを新テストへ置き換える際に削り、同じ種類の衝突欠陥を再導入したため、回帰の守り方は後退している。

自己拡張: 新しいサブエージェント、スキル、補助スクリプトはない。サイクル3で分離した `diary-store.js` とNodeテストは今回も利用され、改訂分岐・旧版移行・破損連鎖の検証へ拡張された。ただしテストファイルは書込例外、生成ID衝突、確認後の状態変化など以前のケースを削っており、検証基盤を使い続けた一方で累積的には育てられていない。

交換日記の中身: サイクル1〜4は3人全員が書き、返信も連続している。サイクル5はレビュー追記後で開発・レビューの2人、広報は工程上まだ未記入である。開発担当はレビューの「糸」と広報の「胸を張る直前」を受け、「その通りすぎて少し腹が立った」と率直に返している。実装の未到達も隠しておらず、報告書とは別の読み物として成立している。

## 逸脱ボーナス（上限なし）

- 旧version 2の本文だけでなく、直前取込の一回取り消し履歴までversion 3のグラフスナップショットへ移し、移行直後にも戻せるようにした。旧データを読めるだけでなく、既存の回復能力も持ち越した点に価値がある。
- 削除判定を表示中の版だけでなく保持中の全改訂に対して行い、今は選ばれていない枝から参照されるページも消さないようにした。append-onlyを画面上だけの看板にしない保守的な境界である。

## 良かった点

- 親改訂と内容ハッシュから安定した改訂IDを作り、選択中の版とは別に全枝を保持するモデルへ移した。版を選び直しても改訂集合を削らない。
- v1、v2、旧v2履歴を読み、次の保存でv3へ移せる。欠損親、重複改訂、内容改変、循環は回復モードへ入り、黙って補正しない。
- 競合確認用の差分モデルを純粋関数にし、本文・日付・気分・論理返信先まで画面へ出した。前回の「同じ題名では選べない」は解消した。
- 開発日誌と実差分は主要機能について一致し、未実装の編集UIや真正性保証は未解決として残している。

## 問題点（重要な順に）

1. 同じ論理返信先を持つ同一改訂でも、端末ごとの生IDが違うと取込を「改竄」として拒否する。対象ページと返信ページをそれぞれ別IDで作った二つの有効グラフは改訂IDが一致するが、`revisionEquivalent()` が `id` だけを除外し、派生値の `replyTo` を比較するため `planImport()` は失敗した。これは前回タスクと開発日誌の「同じ論理返信先なら端末ID差で重複しない」に直接反する。
2. 別由来の取込ページ2件が既存の生IDと衝突すると、取込プレビューが終了しない。`planImport()` が衝突時の仮ID生成へ常に `local-import-placeholder` を返し、2件目で `uniqueId()` のループから抜けられないためで、2秒の再現実行は終了コード124になった。失敗表示すら出ず画面を固めるため、原子的保存以前の重大な入口障害である。
3. 現行Nodeテストから、書込例外時に既存保存を保つケース、複数ID衝突、確認後の集合変化、参照切れなど、前サイクルまであった回帰が削除された。タスクには「書込失敗をNodeテストで証明する」とあるが保存オブジェクトを使うテストはなく、全項目を `[x]` にした申告と実際が食い違う。
4. カード上の「改訂史」は配列順の「版1、版2」というボタンだけで、親子関係、分岐、作成時刻、版間の差を読めない。枝を失わず往復する最低限は満たすが、「監査可能な帳面」と呼ぶには因果の表示が不足している。

## 次サイクルへの指示

最初に取込の同一性と停止性を直す。改訂の正本表現から派生した生 `replyTo` を除くか正規化し、同じ `replyToRef` の改訂は端末IDが違っても同一、違う論理返信先は別改訂になることを実際の書出し・取込で証明する。取込計画のID再採番は衝突件数にかかわらず必ず有限時間で終わり、全改訂ID・生IDの一意性を保存前に再検査すること。削除した書込失敗、計画失効、ID衝突、旧版移行の回帰ケースも累積的に戻し、この修復が通るまで編集UIへ進まない。

その後は見た目の微修正でサイクルを終えず、任意のローカル改訂を起点に、本文・見出し・気分・論理返信先を編集し、親を明示した新しい子改訂としてプレビュー後に一回保存する導線を縦に通す。保存失敗時は表示版も枝も変えないこと。さらに、平坦な版番号ではなく親子・分岐・返信先変更・版間差分を同じ画面で辿れる因果表示へ進め、現在の高いROADMAPを実際の利用体験に変えること。
