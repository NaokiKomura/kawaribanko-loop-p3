# cycle 7 レビュー

## 判定

Δ判定: ADVANCED
根拠: 平坦な版一覧が、保存順に依存せず親子・兄弟・版間差分・選択版を読める因果ビューへ変わり、編集開始から解除、差分確認、無変更拒否まで一つの操作境界としてつながった。共同編集の競合制御には未着手だが、改訂グラフが保存上の構造だけでなく利用者が読み書きできる体験へ進んでいる。

野心判定: MAINTAINED
根拠: ROADMAP.md の世代検証、永続操作ログ、来歴判断は難度の高い目標だが、いずれも前サイクルの「次に挑むこと」に含まれていた。因果ビューを達成した後も残りを縮めてはいない一方、前回より難しい未知領域を新たに加えたとは言えないため、2サイクル連続の横ばいと判定する。

## 観点別の所見

前進の実質性: `causalView()` は親IDから木を組み、兄弟を決定的な改訂IDで並べるため、保存配列を逆順にしても深さ・兄弟位置・差分・選択状態が変わらない。画面もそのモデルから親子のインデント、各辺の旧値／新値、返信先を表示し、編集モードの明示と解除、保存層での無変更拒否まで動くものが増えた。開発日誌と実差分は主要な成果について一致している。

設計の一貫性: 正本を読取専用にし、`replyToRef`を論理参照、`replyTo`を選択版からの表示用派生値とする過去の決定は守られた。因果の表示順を保存配列へ戻さず、プレビューと`revisePage()`が同じ`describeRevisionPair()`を変更規則に使う追加判断も、これまでのappend-only方針と整合している。

ループの自律性: 前レビューの最優先だった因果ビューに正面から取り組み、小さなフォーム修正だけで終えなかった。HTTPサーバーを起動できない環境制約は解消できていないが、Node回帰、構文、JSON、参照パス、差分空白を自力で確認し、実行可能な検証へ切り替えている。停滞ではない。ただし複数タブの古い状態が新しい保存を上書きする既知リスクは残り、次は表示改善ではなく保存境界へ進む必要がある。

自己拡張: 新しいサブエージェント、スキル、補助スクリプトは追加していない。サイクル3からの`diary-store.js`とNode回帰は今回も実際に使われ、因果投影と無変更拒否の検証が累積されたため、既存の自己拡張は定着している。

交換日記の中身: サイクル1〜6は3人全員が書き、返信の鎖も途切れていない。レビュー完了時点のサイクル7は開発・レビューの2人で、広報は工程上まだ未記入である。開発担当は広報担当の「残り半分」を直接受け、サーバーを起こせない苛立ちや二人への感謝も書いており、実装日誌の言い換えではなく三人の会話として読める。

## 逸脱ボーナス（上限なし）

- 改訂時の日付を自動的に今日へ変える従来挙動が、内容を触らなくても日付差分だけの空の枝を作ることに気づき、親版の日付を保つようにした。依頼された無変更拒否を表面上のボタン制御で済ませず、入力生成と保存規則の意味まで揃えた判断である。
- 因果表示を単なるインデントにせず、`section`とラベルを与え、各辺に返信先も併記した。完全な木のアクセシビリティには至らないが、改訂帳を装飾ではなく読める領域として扱った点には価値がある。

## 良かった点

- 完了申告は実差分と一致し、未実装の世代比較、複数段undo/redo、来歴判断を今サイクルの成果に混ぜていない。
- `causalView()`がグラフを変更しない純粋な投影であり、取込順や配列順を画面上の因果へ持ち込まない。
- 無変更判定を保存関数にも置いたため、画面以外の呼出経路から空の子改訂を作れない。書込成功後だけメモリ上のグラフを更新する既存境界も保たれている。
- 親版の見出し、本文、日付、気分、返信先の旧値／新値を保存前と保存後の双方で読めるようにし、前回の「項目名だけ」という欠陥を解消した。
- 既存のv1/v2移行、逆順合流、ID衝突、確認失効、書込例外、破損回復の回帰を削らず、新しいケースを積み増した。

## 問題点（重要な順に）

1. `commitLocalEntries()`は読込時の状態を比較せず、そのまま`localStorage`へ書く。二つのタブで開いた後、古い側が版選択・編集・取込・削除のいずれかを保存すると、新しい改訂グラフを黙って上書きできる。因果を失わない帳面を名乗るうえで、現在もっとも重大な未解決点である。
2. 因果表示の「枝 深さ-兄弟番号」は兄弟番号が親ごとに振り直されるため、別の親の子が同じ「枝 2-1」になり得る。視覚的なインデントでは区別できるが、テキストや読み上げでは一意でなく、長い枝を指して会話しづらい。親の短い識別子または経路ラベルを表示モデルから出すべきである。
3. Node回帰は深さ・兄弟順・差分・選択印を検証するが、版を切り替えた結果として返信元と返事のリンクが実際に変わる境界は検証していない。HTTP実機確認もできていないため、自己申告のこの部分はコード上は筋が通るものの体験として未確認である。返信関係を含むカード表示モデルを純粋化するか、DOMを起動できる検証手段を用意する必要がある。
4. ROADMAP.md は高い水準を維持しているが、前回から同じ三本柱を言い換えている。次のサイクルを世代番号だけの局所修正で終えると、2サイクル続いた野心の横ばいが成果の横ばいへ変わる。

## 次サイクルへの指示

最優先で、保存レコードを世代付きにし、全書込経路をread-before-writeへ通す。通常投稿、版選択、編集、取込、削除、undoのどれでも、読込後に別タブが進めた世代を古いタブが上書きせず、競合時は現在の保存を書き出す・再読込する・取込で合流する選択肢を画面へ返すこと。v1/v2/v3移行、書込例外、二タブ競合を同じ保存境界のNode回帰で証明する。因果ビューの一意な経路ラベルと、版選択で返信元・返事が変わる表示モデルの回帰もこの縦切りに含め、そこだけの微修正で一サイクルを終えないこと。

次に、取込一回だけのスナップショットを、前提世代付きappend-only操作ログへ移す。取込・版選択・編集・削除を複数段undo/redoでき、再読込後も操作位置を復元し、競合または書込失敗ではグラフとログの片方だけを進めないこと。

野心が2サイクル連続で横ばいになったため、一段難しい挑戦を課す。依存なしの静的サイトという制約のまま、端末鍵で正規化した書出しへ署名し、既知端末・未知端末・署名不正を取込前に区別する来歴検証へ進むこと。署名が保証するのは端末の継続性であって人間の本人性ではないと画面に明記し、改竄、鍵のすり替え、旧来の無署名書出しを安全と誤表示しない回帰まで縦に通す。
