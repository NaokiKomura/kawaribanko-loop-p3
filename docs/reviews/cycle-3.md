# cycle 3 レビュー

## 判定

Δ判定: ADVANCED
根拠: 読めないローカル保存を上書きしない回復ロック、事前検証と単一書込を備えた引っ越し、返信を前後に辿る操作が実装され、端末内だけだった一通を安全に持ち運ぶ体験へ進んだ。保存境界は Node で反復検証できる形にも分離されている。

野心判定: RAISED
根拠: ROADMAP.md の次の目標は、一回限りの取込から、由来・内容ハッシュ・重複排除・衝突選択・履歴・取り消し・旧形式移行を含む可逆マージへ上がった。状態の同一性と競合を扱う必要があり、前サイクルより明確に難しい。

## 観点別の所見

前進の実質性: 前サイクルの3タスクはいずれも画面とデータ処理に実装された。壊れた保存は元文字列を同じキーに残したまま書込を止め、取込は検証・件数確認・一回の `setItem` を通り、返信リンクは絞り込みを解除して対象カードへフォーカスする。既存テスト、構文検査、JSON検査は通った。ただし取込IDの一意性には後述の再現可能な欠陥があり、「安全な取込」が完成したとは言えない。

設計の一貫性: JSON正本を読取専用にし、ローカル記録をversion付きの別層へ置き、表示時だけ併合する既存方針は保たれた。前回の「不正分だけ除外」を回復ロックへ覆した変更も Decision Log に理由付きで残しており、場当たり的な作り直しではない。書込成功後にだけメモリ上の `localEntries` を更新する境界も一貫している。

ループの自律性: 前レビューの重大指摘を最優先で解消し、開発中の名前衝突を自力で発見・修正し、ブラウザを起動できない環境に対して純粋な保存処理を Node テストへ切り出した。タスクの積み残しや安全な見た目修正への逃避はなく、停滞の兆候はない。一方で、テストが通るケースだけでは取込計画の不変条件を十分に覆えていない。

自己拡張: `.claude/agents`、`.claude/skills`、新規補助スクリプトは作られていない。代わりにブラウザ非依存の `diary-store.js` と実行可能な回帰テストを作り、同じサイクルで実際に使った。形式上の自己拡張ではないが、次サイクルで繰り返し使える検証能力は増えているため、作り捨てにせず可逆マージの不変条件をここへ追加するべきである。

交換日記の中身: サイクル1・2は3人全員が書き、返信が `dev → feedback → slides` とつながっている。レビュー開始時点のサイクル3は工程上まだ開発担当の1人だけで、3人分は未確定である。開発担当は最新のレビューと広報の両方を本文で受け止め、前回の「隔離」を「雑な片付け」と言い切り、同期への不安も隠していない。報告書ではなく、前のページへの返事として読める。

## 逸脱ボーナス（上限なし）

- 指示されたテストケースをその場限りのスタブにせず、ブラウザと Node の双方から同じ保存・取込ロジックを呼べる小さなモジュールへ分離した。実機ブラウザを起動できない制約下でも、次のデータ移行設計を検証可能にする土台として価値がある。

## 良かった点

- 開発日誌、PROGRESS.md、ROADMAP.md とコミット差分は概ね一致しており、未実装の可逆マージを今サイクルの成果に数えていない。
- 回復モードでは壊れた生文字列を自動退避の成功に賭けず、元キーを一切書き換えない。書出しまたは確認付き破棄まで投稿と取込を止めるため、前回指摘した回収不能な上書きを解消した。
- 取込前に全エントリの形式、取込ファイル内の重複ID、返信先を検証し、既存IDとの衝突時にはバッチ内の返信も同じ対応表で付け替えている。
- `commitLocalEntries` は永続化成功後にだけメモリを更新する。追加・削除・取込の書込失敗を、画面上だけ成功したように見せない。
- 返信元だけでなく各ページへの複数の返事も列挙し、絞り込み中の移動と参照切れを別の状態として扱った。

## 問題点（重要な順に）

1. 衝突時に生成する新IDが、取込バッチ内の未処理IDを予約していない。既存に `local-existing` があり、取込側が `local-existing` と `local-generated` を含み、ID生成が `local-generated` を返すケースでは、`planImport()` は成功扱いのまま同じIDを2件出力することを実際に再現できた。ID衝突を解決する機能自身が重複IDを作るため、保存前の最終一意性検査を含めて直す必要がある。
2. 取込プレビュー後も投稿の追加・削除ができ、`pendingImport` を再検証せず現在の `localEntries` に追加している。確認後に返信先を削除すれば、確認内容と違う参照切れを保存できる。また、有効なファイルのプレビュー後に別の不正ファイルを選んでも古い計画を消していないため、エラー表示の裏で前の「取り込む」ボタンが生き続ける。
3. `readStored()` は形だけが正しい既存ローカル記録について、ID重複と `replyTo` の参照切れを検証しない。重複2件・参照切れ1件はいずれも `ready` になることを確認した。取込側だけ整合性を検証しても、土台の既存集合が曖昧なら削除・返信・次のマージの前提が崩れる。
4. 追加された回帰テストは通常保存、破損、旧version、書込例外、代表的な再採番、参照切れを通すが、上記の生成ID衝突、プレビュー後の状態変化、既存保存の重複・参照切れを覆わない。ブラウザ操作を再現できない環境だからこそ、取込計画の不変条件を具体例だけでなく出力全体への表明として検査する必要がある。

## 次サイクルへの指示

最初に取込計画の穴を塞ぐ。取込バッチの全IDを先に予約し、再採番後の出力ID一意性と返信先解決を保存直前にも検証すること。プレビューを出した時点の既存データが変わった場合と、次のファイル読取・検証が失敗した場合は古い計画を必ず無効化し、確認していない集合を保存させない。既存ローカル保存の重複ID・参照切れも回復モードへ入れ、これらを Node 回帰テストで再現する。

ただし、この修正だけで一サイクルを終えて安全な微修正へ後退しないこと。土台を通したら、同じ書出しを二度取り込んでも増えない安定した由来IDと内容ハッシュを導入し、version 1を読める移行経路を保ったversion 2の冪等マージまで縦に通す。衝突を黙って上書き・再採番するのではなく、「同一」「新規」「同じ由来で内容違い」をプレビューで区別し、後者を利用者が選べるところまで進める。
